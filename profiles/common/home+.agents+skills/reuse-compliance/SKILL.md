# REUSE Compliance

Apply REUSE licensing while following the scope the user requested. For a full independent-maintenance transition of an upstream fork, default the outbound license to `AGPL-3.0-or-later` unless the user selects another license. A request limited to one area, such as REUSE compliance or release setup, does not authorize changes to unrelated licensing or infrastructure. Preserve the rights, notices, and obligations attached to inherited material throughout the work.

## 1. Establish the target and scope

Read repository instructions and relevant `docs/spec/` and `docs/architecture/` files when present. Inspect the working tree, remotes, manifests, license files, file headers, installer, updater, and release configuration before editing. Use `rg` for searches.

Establish these facts from the request and repository:

- Upstream repository and identity, plus the fork point when available.
- Fork owner, repository, module or package identity, and release destination. A GitHub namespace does not establish ownership of an npm package, registry account, or Homebrew tap.
- Maintainer copyright holder text and contribution years. Take the holder text from the user's wording or an existing notice and keep it literal; git metadata can confirm a name and years, but it is not a notice, so never copy an email address or URL from it into a copyright line. When the user names a holder without an email, the name alone is the complete holder.
- Requested outbound license; for a full transition without an explicit choice, use the exact SPDX identifier `AGPL-3.0-or-later`. When the user names a family without `-only` or `-or-later` (for example "GPL-3"), read the repository's existing notice, manifests, and package metadata, use what they already grant, and say which variant you chose. Never narrow an existing grant, such as `-or-later` to `-only`, without asking; ask only when the evidence conflicts.
- Existing publication channels and whether the fork has its own usable releases or package versions.

Ask one focused question if a consequential fact cannot be established. State consequential license or identity changes before editing. A request for an assessment authorizes investigation; a request to perform the transition authorizes local implementation. Keep existing user changes intact.

## 2. Resolve licensing before making licensing changes

Apply the compatibility gate when selecting or changing the outbound license. For a REUSE-only request, identify the licenses already applicable to the files and preserve those choices; the AGPL default applies only to a full independent-maintenance transition. For distribution-only work, check that the affected packages retain their required notices.

Read the actual upstream license text, copyright notices, file-level exceptions, and bundled third-party licenses. Inspect dependencies that are incorporated into the distributed or hosted work; distinguish them from separate tools and remote services. Package metadata alone is insufficient evidence of licensing permission.

Inherited material is not limited to the fork point. In a repository that is not a fork, or in a fork with later additions, search comments and docs for provenance markers: "based on", "adapted from", "ported from", "follows … license", links to gists, Q&A answers, or upstream source files, and vendored directories. Read the actual license of each source and decide per snippet: MIT or Apache-2.0, keep the notices; CC BY-SA 4.0, convertible to GPLv3 only; no license, rewrite or ask for permission as below; a link that only documents behavior, no action.

Before selecting or changing the outbound license, determine whether the requested license is permitted for the fork and compatible with the inherited material and relevant dependencies. Check the exact license versions, `-only` versus `-or-later`, exceptions, and any real choice of alternative licenses. Do not assume that every open source license permits conversion to the target.

**If a conflict blocks the requested outbound license, stop the licensing transition and any ownership changes that depend on it before editing.** Report the affected material, original license, requested license, and conflicting requirement. Ask the user to resolve the conflict; do not silently select another target, drop the material, or proceed with dependent ownership changes. If permission or compatibility cannot be established, pause at the same gate and state what evidence is missing. When compatibility is established, proceed without asking for another generic confirmation.

Changing the fork's outbound license does not transfer upstream copyright or erase upstream grants. Preserve all required copyright notices, permission notices, license texts, disclaimers, attribution, and other conditions. Do not suggest that already released upstream material loses its original license.

For MIT material, keep the upstream copyright notice and the complete permission notice, including the disclaimer. Reproducing the original license in a notice file that is distributed with the material is a valid preservation approach; a link alone is insufficient. Include that file wherever copies or substantial portions of the material are distributed. A retained MIT notice documents inherited obligations; it does not by itself offer the entire fork under MIT as an alternative to the selected outbound license.

For Apache-2.0 material, keep the license copy, mark modified files as modified, keep the upstream copyright, patent, trademark, and attribution notices, and carry the upstream `NOTICE` text when one exists. Apache-2.0 and MIT material may be redistributed under `AGPL-3.0-or-later` once those notices are kept, so give it the single outbound identifier and list the upstream holders in the file's copyright lines instead of adding `OR` or `AND` expressions.

Some licenses do not permit that, so keep their own identifier on those files and say so in the root licensing document:

- The Vim License requires its text to stay with the material and sets conditions on distributing modified versions (section II), so material derived from Vim stays under it.
- `GFDL-1.3-only` text cannot be relabeled as `AGPL-3.0-or-later`.
- CC BY-SA 4.0 converts one way to GPLv3 only, not to AGPL or to "or later". Check the exact version before deciding; a plain "CC BY-SA" in an upstream comment is not evidence.

When upstream has no license, its code is all rights reserved: do not copy it. Ask the user which path to take: obtain permission, rewrite clean-room, or, when the fork is a substantial rewrite, treat the current code as the maintainer's own work.

- Clean-room rewrite of expressive code (a function, module, or file): give a subagent only the behavior to implement and never the original source, then check the result independently against the behavior and compare it with the original yourself.
- Where the only overlap is functional, such as a command, a target name, or a copy step: rewrite it directly with different commands and structure, and say in the report that this is not a strict clean-room.
- Own-work path: measure what survives. Compare the current tree with the last pure upstream commit, never a merge tip that contains the maintainer's own commits. Count the distinct non-trivial lines that remain verbatim and sort them into specification-dictated values, language or framework idioms, imports, credit text, and expressive code. Report the counts and classes, say that a line comparison cannot rule out derivation by structure or sequence, and let the user decide. If they accept, proceed without claiming that permission was obtained, and keep the credits in the project's README.

For other licenses, derive the preservation requirements from their actual terms. Keep required NOTICE material, modification notices, source availability, and license-specific distribution conditions where applicable. Consult primary license texts and authoritative guidance when needed; never invent permission to resolve uncertainty.

## 3. Update licensing metadata when in scope

Use existing repository conventions where they satisfy the intended licensing. For an outbound-license change, make the relevant changes together so file metadata, documentation, and distribution remain consistent. For a REUSE-only request, record the licenses that already apply without selecting a new outbound license:

- When changing the outbound license, add its complete text at `LICENSES/<SPDX-identifier>.txt`, using `reuse download <SPDX-identifier>` or an authoritative source, and make the root `LICENSE` a verbatim copy of the same text with nothing added. Hosting platforms detect the license by matching `LICENSE` against the license text (GitHub uses licensee): a short notice placed before the GPL-3.0 text dropped the match from exact to `NOASSERTION` (87% similar), and a one-line copyright left only a 0.9-point margin over the 98% threshold. Check detection with `licensee detect` on a copy of `LICENSE` in a plain directory, because in a git repository it reads the committed revision. Platforms cannot tell `-only` from `-or-later`, so that grant is carried by the file headers and the root `NOTICE.md`. Keep the root `NOTICE.md` as the licensing document: it states the fork's outbound license, identifies upstream provenance, and carries required original notices. Preserve custom license texts without replacing them with a generic template.
- Associate accurate `SPDX-FileCopyrightText` and `SPDX-License-Identifier` information with covered files. Preserve upstream holders and years. Add the maintainer to new or genuinely modified work according to repository policy; do not assign them copyright over every inherited file merely because the project was forked.
- Declare licensing with an SPDX header in the file by default, license line first and copyright holders after it (format below). Use a `REUSE.toml` table only for Markdown (see below) and for files where a header is unsafe (see below), and keep license identifiers and holders out of `REUSE.toml` for every other file. The test is whether the file can safely hold a comment, not what kind of file it is: TOML and YAML configuration takes a header like any source file.
- Do not put in-file headers in Markdown by default. Agents and readers load `AGENTS.md`, `README.md`, and docs whole on every read, so a header costs tokens each time, and some files open with YAML frontmatter. Cover all Markdown with one `**/*.md` table in `REUSE.toml`, and add in-file headers only when the user asks. REUSE still reads the body of a headerless file, so a Markdown file that quotes license text, SPDX tags, or `©`/"Copyright" lines needs its own `override` table or a sidecar. Keep the `**/NOTICE.md` override table last.
- For files that safely support comment syntax, add an SPDX header with the `SPDX-License-Identifier` line first and the `SPDX-FileCopyrightText` lines directly after it, with no blank or empty comment line between them. Never put the copyright first, and never separate the two with a `//` or `#` spacer line. Write one block, then a blank line before the rest of the file, as in `// SPDX-License-Identifier: ...` followed by `// SPDX-FileCopyrightText: ...`; several holders take consecutive copyright lines. Write the holder exactly as established; `SPDX-FileCopyrightText: 2026 Jane Doe` is a complete line when no email was given. Appending an address from git configuration is not completeness, because that address was never part of the notice the user supplied. Check headers written by tools, since a default template can reverse the order or insert a spacer. Use the project's contribution range for the maintainer, and add each upstream holder to the same header. Preserve shebangs, encoding declarations, and compiler directives in their required positions.
- A header is unsafe where a comment changes meaning. Check each class before annotating: JSON and lockfiles; integrity-protected files such as sops-encrypted secrets (editing breaks the MAC), signatures, and checksummed manifests; files the build reads and writes out verbatim, where a header changes the generated artifact; an XML prolog that must be on line 1; first-line directives such as shellcheck `shell=`, editor modelines (they must stay within the first lines the editor scans), and plugin pragmas; generated or byte-compared output; files an application rewrites and so drops the comment; files whose whole content is a value; templates whose copies would inherit the header; and formats where `#` is data. For these use a `REUSE.toml` table that lists them by glob: by extension for formats that hold no comments at all (`**/*.json`, `**/*.lock`), and by path for the other classes.
- Use a `.license` sidecar only for a single file that the rules above cannot cover, typically one whose body would be misread, such as a file that quotes SPDX tags or upstream license text in prose, or that holds a `©` or "Copyright" string in its data (a tag name or a message, for instance): REUSE ignores the body when a sidecar exists, while a header does not stop it from being parsed. `reuse annotate --skip-existing` reports such files as already containing REUSE information, so read its skip list instead of assuming they had a notice.
- Run `reuse annotate` with a template that writes the license line first, an explicit `--style` for files without a known extension, and no year when the range is fixed. Supply the template as `.reuse/templates/<name>.jinja2` and remove that temporary directory afterwards unless the user wants it kept. Try a bulk run on a throwaway clone first (use `--no-hardlinks` when the scratch space is on another filesystem), annotate files with unrecognised styles in a second pass with an explicit `--style`, then run the repository's formatter: a header can make it change the blank line that follows (YAML `---`, Python top-level definitions). It rewrites an existing header comment and can erase an upstream notice, so annotate such files by hand and check afterwards, after formatting, that every added line is a header line and nothing was deleted.
- Preserve licenses and notices for third-party files, assets, and snippets. Apply the target license to fork material only where the licensing analysis permits it. Do not indiscriminately overwrite every SPDX identifier or introduce `OR` expressions that offer an unauthorized alternative license.
- Keep third-party notices beside the material they cover. Put a `NOTICE.md` with the full license text in the directory of each derived part, repeat a shared text such as Apache-2.0 in every sibling instead of pointing elsewhere, and keep the root `NOTICE.md` as an index table of material, upstream, license, and notice location. Index only material whose license imposes notice obligations; provenance without such an obligation, such as an own-work rewrite of an unlicensed upstream, belongs in the project's own credits, not in the root `NOTICE.md`. Name the file `LICENSE` when a directory is taken wholesale from one upstream, and `NOTICE.md` when the material is modified or mixed. Give every notice file one format: a description line, then upstream, license, modifications, and distribution, then the verbatim license text. Do not add a sentence that the modifications fall under the root license; the headers already say so. Fence the quoted license text as a `text` code block: Markdown reflows the lines into prose and reads a clause line such as `0. Definitions.` or `(a)` as a list and `*` as emphasis, so unfenced text is no longer the license it claims to quote.
- A notice file's own copyright is the maintainer's, because the upstream holders belong to the material and the quoted license text must not be read as the notice's copyright. Declare it with a `.license` sidecar, or with one `override` table for `**/NOTICE.md` placed last so it wins over directory tables.
- When changing the outbound license, update license metadata, badges, documentation links, and release archive contents together. Every license text and notice required by shipped material must accompany its distribution; moving a notice from `LICENSE` to `LICENSE.md` requires updating archive manifests and every live reference.

Use `REUSE.toml` version 1 for the tables that remain after headers and sidecars. Inspect existing annotations before adding more: `*` does not cross directory separators, `**` does, and the last matching table in one file wins. The default `closest` behavior preserves file-level information; `aggregate` adds information, while `override` replaces closer information. Choose deliberately and never use broad overrides to conceal third-party licensing. Preserve one coherent annotation scheme; do not leave both `REUSE.toml` and `.reuse/dep5` active.

Keep `LICENSES/` for licenses actually referenced by covered files. When an original license is retained solely as a preservation notice, carry it in a notice file beside the material, or in the root `NOTICE.md` when the whole project is derived from one upstream. A license still applied to inherited or third-party files also needs its corresponding text in `LICENSES/`.

## 4. Move requested infrastructure to fork ownership

Inventory upstream references by their purpose before replacing them. Apply only the surfaces included in the request or needed to make the requested transition work. Move operational destinations to the fork only when a fork-owned destination exists. Preserve upstream provenance, copyright attribution, required notices, and references to independent dependencies.

| Surface | Transition when in scope |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Module and package identity | If the fork will publish or install under a new identity, update the manifest, internal imports, install commands, and relevant build metadata. Confirm the target with the user and respect ecosystem rules before changing a public package identity. |
| Installation and updates | If the project has installer or update paths, point them to usable fork-owned artifacts and release notes. Keep archive naming and platform selection consistent with the build configuration. Do not invent a destination. |
| Release publishing | Point active publishing workflows to destinations the fork controls. Remove or disable inherited integrations the fork cannot use, with their now-unused secret references and documentation. |
| Repository support | Update CI/release badges, homepage and repository metadata, issue links, security-report links, and support contacts that are meant to serve this fork. |
| User documentation | Describe working fork installation and maintenance paths when they change. Retain upstream attribution and explain publication prerequisites. |

Keep the existing executable name, commands, configuration paths, data formats, and runtime behavior unless a requested identity change requires otherwise. Do not bulk-replace an upstream owner's name in legal notices or change unrelated dependencies.

If the fork has no usable release or package version, provide a working source-build path and clearly identify release-based commands as requiring a future fork publication. Inherited tags alone do not prove that fork binaries exist. Never make installation or updates silently fall back to upstream artifacts. Treat a missing fork release as unavailable, using the project's existing failure behavior.

Do not invent a replacement Homebrew tap, registry, credential, or publishing service. Remove or disable an unsupported upstream integration instead. Delete orphaned configuration resulting from these changes. Keep translations, branding assets, and agent instructions unless the user requests their removal or their contents must be updated for the transition.

## 5. Finish according to the requested scope

Update existing intent docs when the transition changes their contracts or architecture; do not create `docs/spec/` or `docs/architecture/` merely for this task. Repeated execution should complete missing work without duplicating notices, headers, annotations, or release configuration. If the transition is already complete, report that state without creating cosmetic changes.

For implementation work, run relevant local checks such as `reuse lint`, the repository's formatter and pre-commit checks, existing builds/tests, and a release tool's validation or snapshot mode when available. `reuse lint` passing does not show that each file resolves to the intended license, so also run `reuse spdx` and check three things: the license per file (for example, only the known exceptions are not the outbound license), the copyright lines (none that look like license prose), and every file whose precedence you changed. For each file you annotated, compare its content minus the header against its previous version, and run the syntax check or linter the file's language has. When the outbound license changed, confirm that `licensee detect` recognizes the root `LICENSE`. Examine produced archives for required licensing material. A linter parses the source, never the rendered page, so also open each notice file you wrote as a rendered document and confirm its license text is still one literal block; when the repository's formatter rewrites Markdown, re-read that block after it runs.

Tell the user about side effects of editing files, such as a direnv `.envrc` that must be allowed again after its content changes. Headers also change source hashes: where a build system hashes sources, compare build or evaluation outputs before and after (for Nix, a host's `toplevel` drvPath from the committed revision against the working tree) and tell the user which deployables change and which services restart on the next deploy. Where the repository runs hooks before commit, offer to run `reuse lint` there; do not add the hook unasked. Search for remaining upstream operational destinations and stale file references, classifying intentional provenance references separately. Avoid running real installers, updaters, or publishing workflows as checks; ask before external side effects. For assessment-only requests, investigate without editing or running state-changing checks.

Follow the repository's commit policy. Use `git-commit` when committing and stage only the changes made for this task. Where coherent, separate license/REUSE adoption from infrastructure ownership; each commit must keep its references and packaging consistent. Do not force exactly two commits. Pushes, tags, releases, registry publication, remote settings, and history rewrites require their own authorization.

Finish with a concise report containing the outbound license if selected or changed, preserved upstream obligations, changed ownership surfaces, checks actually performed or skipped, and any remaining external setup. Claim only the behavior that was exercised. If licensing blocked the transition, report the blocking evidence and the decision needed to resume.

## Primary references

Consult these when the relevant rule needs confirmation. Read other original license texts when the target repository uses them.

- [REUSE Specification](https://reuse.software/spec-3.3/) — coverage, license texts, headers, annotations, and precedence.
- [REUSE download](https://reuse.readthedocs.io/en/stable/man/reuse-download.html) and [REUSE lint](https://reuse.readthedocs.io/en/stable/man/reuse-lint.html) — license installation and compliance checks.
- [MIT license text](https://spdx.org/licenses/MIT.html) — original notice preservation.
- [GNU AGPL version 3](https://www.gnu.org/licenses/agpl-3.0.html) — target license terms; use the exact requested SPDX variant.
